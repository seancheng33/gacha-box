## 1. 项目概述

### 1.1 一句话定义

一个多用户抽盲盒 Web 小游戏：注册登录后消耗金币抽卡，卡片分五个等级（普通/稀有/史诗/传说/SSR），配开盒动画、图鉴收集、排行榜与管理员后台，交互风格模仿 WorkBuddy 抽奖（点击 → 开盒动画 → 翻卡揭晓）。

### 1.2 目标

- G1 交付完整闭环：注册 → 签到领金币 → 单抽/十连 → 图鉴收集 → 排行榜攀比
- G2 抽卡公平可审计：概率、保底在服务端实现，每笔抽卡落库可回溯
- G3 工程过程规范：小迭代交付、核心逻辑测试先行（XP），每轮迭代附功能测试报告
- G4 可演进：卡面可从 emoji 占位平滑替换为本地 ComfyUI 出图；架构满足未来挂到服务器

### 1.3 非目标（明确不做）

- 3D、联网对战、实时多人交互
- 真实支付、商业化
- 卡片战斗数值系统（纯收集向）
- 高并发（单 SQLite 文件足够，不引入 MySQL/Redis）

## 2. 需求分析

### 2.1 用户故事与验收标准

| # | 用户故事 | 验收标准 |
|---|---------|---------|
| US1 | 作为访客，我可以注册账号 | 用户名唯一（3~20 字符）；密码 ≥ 6 位，scrypt 哈希入库；重名注册明确报错；注册即赠 1000 金币 |
| US2 | 作为用户，我可以登录/退出 | 会话 cookie（HttpOnly + SameSite=Lax）；未登录访问抽卡页 302 回登录页；连续失败 5 次限频 10 分钟 |
| US3 | 作为登录用户，我可以每日签到 | 每自然日一次 +100 金币；当日重复签到返回提示而非报错；页面上可领状态醒目 |
| US4 | 作为登录用户，我可以单抽 | 金币 ≥ 100 才可抽；结果由服务端概率引擎决定；扣款、落流水、入册在同一事务内 |
| US5 | 作为登录用户，我可以十连 | 消耗 900（9 折）；保底：至少 1 张「史诗」及以上；动画可跳过 |
| US6 | 作为登录用户，我受硬保底保护 | 累计 60 抽内必出 SSR；SSR 出货即重置计数；保底进度对用户可见（增强抽卡预期） |
| US7 | 作为登录用户，我可以查看图鉴 | 30 张卡全部展示，未拥有显示剪影/问号；已拥有显示卡面与持有数 ×N；支持按等级筛选；显示总收集进度 |
| US8 | 作为登录用户，我可以查看排行榜 | 三个榜单：收集度（拥有的不同卡数/总数）、SSR 数量、累计抽数；展示用户名与名次 |
| US9 | 作为管理员，我可以管理卡池与参数 | 管理员登录后可见后台：增删改卡、调整各级概率（校验合计 100%）、给用户发金币；普通用户访问 403 |

### 2.2 关键决策记录（ADR 摘要）

| 决策 | 结论 | 备选与理由 |
|------|------|-----------|
| 后端框架 | Flask | FastAPI 略重（本规模用不上异步与类型体系）；Django 为抽卡游戏过重（admin/ORM 用不上其两成功能）；纯前端无法满足多用户 |
| 存档 | SQLite 单文件 `gacha.db` | 零运维、可拷贝备份；上线压力变大再迁移，表结构按 SQL 标准写降低迁移成本 |
| 等级体系 | 中文五级：普通/稀有/史诗/传说/SSR | 用户定稿；全中文界面统一 |
| 概率分布 | 55% / 28% / 12% / 4% / 1% | 建议值（约每 100 抽 1 个 SSR，配合 60 抽硬保底体感合理），后台可调 |
| 经济数值 | 注册 1000 / 签到 +100 / 单抽 100 / 十连 900 | 新用户当天可玩 1 次十连 + 1 次单抽；十连 9 折制造「攒着抽」的决策感 |
| 重复卡 | 仅计数 ×N（碎片/合成系统不做） | 用户定稿；图鉴需求最简，未来可加碎片字段扩展 |
| 卡面素材 | emoji + 等级色边框 + CSS 特效起步 | cards 表预留可空 `image` 字段，后期换 ComfyUI 出图不改表结构 |
| UI 主题 | 深色（默认）+ 浅色，CSS 变量 + `html[data-theme]` 切换，选择存 localStorage | 只覆盖 `:root` 变量即可换肤，不碰模板；稀有度色改走 `.r1`~`.r5` 类，避免浅底上 SSR 金色文字对比度不足 |
| 运行范围 | 本地开发、按上线标准设计 | CSRF/密码哈希/限频从迭代 0 就做，避免返工 |

### 2.3 非功能需求

- N1 安全：见第 6 章（按上线标准）
- N2 性能：页面响应 < 100ms（本地）；一次十连（含 10 次入库）< 200ms
- N3 可移植：项目目录整体拷贝到任何有 Python 3.10+ 的机器，`pip install -r requirements.txt` + 一条命令即可跑
- N4 可审计：任何一次抽卡都能从 draws 表回溯出「谁、何时、哪一批、出了什么」

## 3. 系统架构

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│ 表现层（浏览器，零依赖原生 HTML/CSS/JS）                   │
│  登录/注册页 │ 抽卡页（动画+跳过） │ 图鉴页 │ 排行榜 │ 后台 │
└───────────────┬─────────────────────────────────────────┘
                │ HTTP（表单 POST + CSRF token）/ JSON
┌───────────────▼─────────────────────────────────────────┐
│ 应用层（Flask，单体但内部分四个模块）                       │
│  auth 认证会话 │ gacha 抽卡引擎 │ collection 收集/图鉴      │
│               │ economy 金币签到 │ admin 管理后台 │ rank 榜 │
└───────────────┬─────────────────────────────────────────┘
                │ SQL（参数化查询，WAL 模式）
┌───────────────▼─────────────────────────────────────────┐
│ 数据层（SQLite 单文件 gacha.db）                           │
│  users │ cards │ draws（流水） │ collections（持有）        │
└─────────────────────────────────────────────────────────┘
```

### 3.2 模块职责（高内聚，单文件项目内按包组织）

| 模块 | 职责 | 不负责 |
|------|------|--------|
| `auth` | 注册、登录、退出、会话管理、限频 | 金币增减（那是 economy 的事） |
| `economy` | 金币余额读写、签到、注册赠送 | 抽卡判定 |
| `gacha` | 概率表、抽卡判定、双保底、十连批量、流水落库 | 入册（调用 collection） |
| `collection` | 入册/累加持有数、图鉴查询 | 概率 |
| `rank` | 三个排行榜聚合查询 | — |
| `admin` | 卡池 CRUD、概率校验与热更新、发金币 | 普通用户任何页面 |
| `static/templates` | 页面与动画（动画纯 CSS keyframes + 少量 JS） | 业务判定（前端永远不算概率） |

### 3.3 技术选型理由（浓缩）

1. **Flask**：本项目的复杂度集中在「游戏规则正确性」而非「框架能力」，微框架让视线始终落在业务上；Jinja2 模板 + Flask 内置 session 足以覆盖需求。
2. **SQLite + WAL**：单写者场景下性能绰绰有余；WAL 模式让读写不互相阻塞，避免抽卡高峰（自己和朋友点得快）时出现 `database is locked`。
3. **原生 JS/CSS**：抽卡动画是 transform/opacity 的组合，引 CDN 库反而增加首屏负担与离线不可用风险。
4. **不引 ORM**：表就四张、查询就十来条，直接 `sqlite3` + 参数化 SQL，代码更短、行为更透明、SQLite→MySQL 迁移时也只是换驱动。

### 3.4 核心时序：一次单抽

```
浏览器                 Flask                     SQLite
   │  POST /draw (csrf)   │                          │
   │─────────────────────>│ 登录检查 + CSRF 校验       │
   │                      │ BEGIN IMMEDIATE          │
   │                      │  扣金币(余额不足→回滚400)  │
   │                      │  概率引擎判定等级→选卡      │
   │                      │  硬保底检查/重置           │
   │                      │  draws 落流水             │
   │                      │  collections 入册/累加    │
   │                      │ COMMIT ─────────────────>│
   │<─────────────────────│ 返回结果 JSON（卡+余额+保底进度）
   │  播放开盒动画 → 揭晓   │
```

要点：**判定与扣费同事务**，任何一步失败整体回滚——绝不能出现「扣了钱没出货」或「出了货没记账」。`BEGIN IMMEDIATE` 拿写锁，防止十连并发下余额竞态。

## 4. 数据设计

### 4.1 表结构

**users** — 用户

| 字段 | 类型 | 约束/说明 |
|------|------|-----------|
| id | INTEGER | PK AUTOINCREMENT |
| username | TEXT | UNIQUE NOT NULL，3~20 字符 |
| password_hash | TEXT | NOT NULL，`scrypt`（盐内置） |
| coins | INTEGER | NOT NULL DEFAULT 1000，CHECK(coins>=0) |
| pity_count | INTEGER | NOT NULL DEFAULT 0，距上次 SSR 的连续抽数（硬保底计数） |
| is_admin | INTEGER | NOT NULL DEFAULT 0 |
| last_checkin | TEXT | 可空，YYYY-MM-DD，签到去重用 |
| created_at | TEXT | NOT NULL，注册时间 |

**cards** — 卡池（预置 30 张，运维梗主题）

| 字段 | 类型 | 约束/说明 |
|------|------|-----------|
| id | INTEGER | PK |
| name | TEXT | NOT NULL UNIQUE，卡名 |
| rarity | INTEGER | NOT NULL，1~5（普通/稀有/史诗/传说/SSR） |
| emoji | TEXT | NOT NULL，卡面占位 |
| image | TEXT | 可空，预留 ComfyUI 出图路径 |
| description | TEXT | NOT NULL，一句梗文案 |
| enabled | INTEGER | NOT NULL DEFAULT 1，后台可下架 |

**draws** — 抽卡流水（只增不改）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER | PK |
| user_id | INTEGER | FK→users |
| card_id | INTEGER | FK→cards |
| batch_id | TEXT | 同一次单抽/十连共享一个 UUID，审计用 |
| created_at | TEXT | 抽卡时刻 |

**collections** — 持有

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | INTEGER | 复合 PK 一半，FK→users |
| card_id | INTEGER | 复合 PK 一半，FK→cards |
| count | INTEGER | NOT NULL DEFAULT 1，重复抽到累加 |
| first_at | TEXT | 首次获得时间（图鉴「新！」标记用） |

### 4.2 关系

users 1:N draws；users 1:N collections；cards 1:N draws；cards 1:N collections；collections 是 users×cards 的多对多关联表，以 `(user_id, card_id)` 为主键天然去重。

### 4.3 设计说明

- **为何记流水**：概率争议的唯一证据链；也是统计测试核对线上分布的数据源。只增不改，方便未来归档。
- **为何 pity_count 放 users**：保底是「用户级」状态，跟随账户而非卡池。
- **为何 cards.enabled**：管理员可临时下架某卡（如文案翻车），不必删行破坏流水外键。
- **索引**：draws(user_id, created_at) 一个足矣（排行榜与审计查询），其余表规模太小不建。

## 5. 核心算法设计

### 5.1 概率引擎（TDD 第一对象）

- 概率表为 `{rarity: weight}`，后台改概率后写入 `app_config` 键值表并缓存于内存，改完即时生效。
- 随机源：`secrets.SystemRandom()`（操作系统熵源，不可预测、不可被客户端种子攻击）。
- 判定即「加权抽段」：累计权重区间内查找，O(等级数)，无需循环。

### 5.2 双保底

```
单抽判定(card, pity):
    if pity == 59:                 # 第 60 抽（0 起数）
        card = 从 SSR 池强制抽取
        pity = 0
    else:
        card = 概率引擎正常抽取
        pity = card.rarity == 5 ? 0 : pity + 1
    return card, pity

十连判定:
    连续执行 10 次单抽判定
    若 10 张中无 rarity>=3（史诗+）:
        将其中一张（固定取第 1 张）替换为「史诗」档强制抽取
    （十连保底不干扰硬保底计数，计数随每次实际出货更新）
```

边界约定：强制保底出货同样落流水并在卡面上标注「保底」角标——诚实展示比伪装欧气更有口碑。

### 5.3 事务与并发

- 所有「扣费+出货+入册」包在 `BEGIN IMMEDIATE ... COMMIT`，异常整体回滚。
- SQLite 开 WAL 模式（`PRAGMA journal_mode=WAL`），读写并发不锁死。
- 十连是**一个事务**：要么 10 张全部成功，要么一分钱不扣。

### 5.4 金币经济平衡

| 数值 | 每日纯签到玩家 | 含初始 1000 的新用户 |
|------|--------------|---------------------|
| 日均可抽数 | 1 次单抽 | 当天 1 十连 + 1 单抽 |
| 期望出 SSR | 自然概率约 100 抽/个；硬保底兜底 60 抽 | 1000+100 金币 ≈ 11 抽/天，第 6 天起每 9 天可攒一次十连 |

签到 +100、十连 900 的组合让「每天上线点一下」成为习惯回路（这正是 WorkBuddy 抽奖的留存心理），又不至于让金币通胀到 SSR 廉价化。

## 6. 安全设计（按上线标准，第一天就做）

| 威胁 | 对策 |
|------|------|
| 密码泄露 | `werkzeug.security.generate_password_hash`（scrypt 默认），绝不存明文/可逆加密 |
| 会话劫持 | cookie `HttpOnly; SameSite=Lax; SecretKey` 从环境变量/启动时自动生成 |
| CSRF | 所有状态变更 POST 携带 per-session token，模板统一注入，服务端校验 |
| SQL 注入 | 全部参数化 SQL，字符串拼接 SQL 出现在 code review 清单里（自查项） |
| 暴力破解 | 登录失败计数：同用户名 5 次失败锁 10 分钟（内存字典即可，重启放行可接受） |
| 越权 | 每个路由显式检查 `session['uid']`；admin 路由额外检查 `is_admin`，默认 403 |
| 抽卡伪造 | 前端零判定权；金币不足/未登录在事务最前端拒绝 |
| 机密配置 | SECRET_KEY 不入库不入仓，`.env` 模式 + `.gitignore` |

上线服务器时的增量清单（现在不做，文档挂账）：HTTPS 强制、CSRF 改 `SameSite=Strict` 评估、限频改持久化（SQLite 表）、备份策略（`gacha.db` 定时拷贝）。

## 7. XP 工程实践与迭代计划

### 7.1 工程纪律

1. **小步提交**：每个用户故事完成即 commit（消息格式 `US4: 单抽事务闭环`）。
2. **测试先行**：第 8 章测试清单中「概率/保底/事务」三类必须在实现前先写好测试骨架。
3. **每迭代可运行**：迭代结束的代码必须能 `python app.py` 起服务并通过验收演示。
4. **功能测试报告**：每轮迭代附 `test_gacha.py` 输出（用户全局规则：每次代码变动都要做功能测试）。
5. **重构窗口**：迭代边界允许小重构，但「先让测试绿，再动结构」。

### 7.2 迭代计划

| 迭代 | 交付内容 | 验收演示 |
|------|---------|---------|
| 0 地基 | 建库脚本、注册/登录/退出、限频、签到送金币、项目骨架（Flask 起服务） | 浏览器注册→登录→签到 +100 |
| 1 能玩 | 概率引擎+统计测试、单抽（事务）、图鉴页（等级筛选/×N/剪影）、卡池 30 张预置 | 抽出五等级各验证；十万次抽样分布过关 |

## 8. 测试策略

| 层 | 用例 | 工具 |
|----|------|------|
| 概率 | 10 万次单抽后各等级频率与理论值偏差 < 0.5 个百分点；权重为 0 的等级永不出现 | unittest + 固定种子的独立 RNG 注入（引擎接受 rng 参数） |
| 保底 | 第 60 抽必出 SSR；59 抽内出货正确重置；十连无史诗时强制替换生效 | 边界用例 + 注入 rng 序列 |
| 事务 | 余额不足时 0 扣款 0 出货；十连中途注入异常整笔回滚 | 临时 sqlite 内存库 |
| 认证 | 注册重名、密码短、登录失败 5 次限频、未登录 302 | Flask test client |
| 收集 | 重复卡 count 累加；图鉴未拥有显示剪影；收集度计算正确 | test client |
| 集成 | 全流程：注册→签到→十连→图鉴→排行榜（模拟端到端脚本） | test client 串联 |

统计测试说明：概率引擎设计为 `draw(rng)` 接受注入的随机源——测试里用 `random.Random(42)` 保证可复现，生产里用 `secrets.SystemRandom`。这是可测性设计（依赖注入）的直接体现。

## 9. 风险与待定项

| # | 风险/待定 | 应对 |
|---|----------|------|
| R1 | emoji 在不同系统渲染不一致（Windows/手机） | 卡面核心信息不依赖 emoji（卡名+等级色为主），emoji 仅装饰 |
